# VEDIO-AGENT 视频工作台业务流程规划

## 来源

本规划来自用户提供的业务流程图 `mermaid-diagram.png`。该图定义了视频工作台从内容策略、脚本、素材、作品、发布到数据反馈和优化学习的端到端走向。

## 总体走向

视频工作台不是单页脚本工具，而是围绕短视频生产闭环的业务应用：

```text
内容策略规划 -> 脚本编辑器 -> 素材管理中心 -> 作品管理中心 -> 发布与数据看板
      -> 内容分发平台 -> 数据分析服务 -> 优化学习 Agent -> AI Agent Orchestrator
```

底层由 `AI Agent Orchestrator` 统一调度选题生成、脚本生成、素材检索、视频生成、发布排程和优化学习等 Agent；Workflow Engine / DAG 调度器负责任务拆解、并行执行、失败重试和状态机管理；LLM / Multimodal Model Layer 负责文本生成、Embedding、TTS、Prompt 优化和第三方视频生成模型调用。

## 前端一级菜单

视频工作台前端一级菜单应按业务工作流组织，而不是只按技术模块组织：

菜单配置应由数据库持久化并通过后端接口返回给 `apps/video-agent`。前端不得继续把 6 个 Agent 硬编码为一级导航；Agent 可作为二级菜单、模块状态或执行状态出现，但一级菜单以业务流程为准。

1. **内容策略**
   - 对应图中 `内容策略规划`、用户画像/账号系统、数据回流和优化学习入口。
   - 面向运营人员的选题池、热点趋势、账号定位、受众画像、策略建议、优化建议。
   - 后续连接 `选题生成 Agent` 和 `优化学习 Agent`。

2. **脚本创作**
   - 对应图中 `脚本编辑器`、`脚本生成 Agent`。
   - 当前已有脚本生成、脚本列表、时间轴对照详情、状态流转能力继续保留在此菜单。
   - 后续扩展脚本版本、分镜确认、Prompt 参数、生成记录和人工编辑。

3. **素材管理**
   - 对应图中 `素材管理中心`、素材管理服务、素材检索 Agent。
   - 管理素材库、素材标签、语义检索、素材候选、素材替换、素材授权和素材清单确认。
   - 后续连接 Embedding 模型和素材检索服务。

4. **作品生产**
   - 对应图中 `作品管理中心`、视频生成管理服务、视频生成调度 Agent。
   - 管理模板选择、配音、字幕、镜头合成、视频生成任务、成片预览和重生成。
   - 后续连接 TTS、Runway、Pika、可灵、HeyGen / Avatar 等第三方模型或服务。

5. **发布运营**
   - 对应图中 `发布与数据看板`、发布分发服务、发布排程 Agent、内容分发平台。
   - 管理平台账号、发布平台、标题封面标签、发布时间、发布状态、发布失败重试。
   - 分发平台包括抖音 / TikTok、YouTube Shorts、B站、小红书、数据回流系统。

6. **数据分析**
   - 对应图中 `数据分析服务` 和发布数据回流。
   - 监控播放、完播、互动、转化、平台表现、内容表现、脚本/素材/发布时间效果。
   - 为优化学习 Agent 提供反馈输入。

7. **工作流任务**
   - 对应图中 `Workflow Engine / DAG调度器`。
   - 展示任务拆解、并行执行、失败重试、状态机管理、跨 Agent 任务链路和运行日志。
   - 面向运营与管理员的任务可观测入口，但平台级 Worker、队列和系统日志仍归 `admin/`。

## Agent 与能力分层

前端菜单不直接暴露所有底层 Agent，但每个菜单要能看到相关 Agent 的执行状态和产物：

- `选题生成 Agent`：服务内容策略和脚本创作前置选题。
- `脚本生成 Agent`：服务脚本创作，生成结构化脚本和分镜。
- `素材检索 Agent`：服务素材管理和作品生产，生成素材候选与匹配结果。
- `视频生成调度 Agent`：服务作品生产，编排 TTS、字幕、模板、视频模型和成片任务。
- `发布排程 Agent`：服务发布运营，管理多平台发布时间和失败重试。
- `优化学习 Agent`：服务内容策略和数据分析，基于发布数据给出策略优化建议。

### 对话式 Agent Runtime

- 所有业务 Agent 的对话能力应接入统一后端 Runtime，而不是在各页面各自实现孤立聊天接口。
- 第一版 Runtime 使用 `agent_conversations` 保存会话，使用 `agent_messages` 保存连续消息，单轮用户消息触发的运行继续写入 `agent_runs` 和 `agent_steps`，方便后续回放、评测、工具审计和成本统计。
- Runtime 通过 `agent_type` 路由到业务 adapter；当前已接入 `script` adapter，支持读取绑定脚本、调用 LLM 生成结构化分镜补丁、更新指定分镜并返回 Agent 回复。
- 脚本创作后续应统一为单一脚本 Agent 对话入口：无脚本时通过对话生成脚本，有脚本时通过同一对话修改脚本；右侧主操作区不应并列展示独立“生成脚本”大表单和“脚本 Agent 对话”输入框。
- 脚本生成仍需要项目上下文和 `topic`、`style`、`scene_count` 等业务参数，但这些参数应由对话解析、Agent 追问或对话面板内的紧凑快捷控件收集，而不是恢复成独立生成大表单。
- 后续 `topic`、`material`、`video`、`publish`、`optimization` adapter 应复用同一会话、消息、运行记录和工具步骤接口。
- Skill、MCP 和 Tool Registry 尚未完整落地时，业务 adapter 可先以内置工具步骤记录 `read_script`、`update_scene` 等动作；后续替换为统一 Tool/MCP Gateway 时，不应改变前端对话 API 语义。
- 当前只完成后端基座和脚本 Agent 接入；前端聊天面板属于 `apps/video-agent` 页面改造，仍需先更新 Pencil 原型并获得确认。

## 项目、选题与脚本关系

- `projects` 表示内容账号、账号方向或内容生产边界，承载策略、选题、脚本、素材、作品、发布和数据回流等产物；前端统一展示为“账号”，不得硬编码 `project_id`。
- `projects.strategy_profile` 保存结构化账号策略；账号策略只在“内容策略 / 账号策略”维护，不在当前选题池重复展示编辑入口。
- `content_topics` 承载独立选题生命周期 `idea -> approved -> scripted -> archived`；原始批次和补充批次按主题组聚合，批次只承担生成来源和审计。
- 脚本生成必须绑定真实项目和选题，保存 `scripts.topic_id` 与 `scripts.content.topic_snapshot`；成功后把选题更新为 `scripted`，保证项目、选题和脚本链路可追踪。
- Full Crew 是视频工作台的正式作品生产模式，必须绑定现有 `projects` 和 `content_topics`；经制作 Gate 批准的剧本、镜头和作品写入现有 `scripts`、`scenes`、作品及生成任务业务模型。虚拟制作团队的 `ProductionState` 只保存制作过程版本、协作建议和审计证据，不得成为与现有视频业务平行的第二套正式数据。
- Full Crew 只允许从 `active` 当前账号下的 `approved` 选题启动；同一 Topic 同时只允许一个 active 制作意图，v1 每个制作意图只允许一个 Run，活跃期间禁止修改或软删除选题并阻止账号归档。编剧产出的 `StoryBible + CharacterBible[] + ScriptDraft` 必须作为同一 `ScriptPackage` 原子审批；批准后以确定性映射在同一事务内创建正式 `approved` 脚本与分镜并把选题更新为 `scripted`，不得二次审批或在 Gate 后调用 LLM 转换格式。
- Full Crew 的 Brief、Script 和 Production Package reject 使用有界 revision epoch；旧产物和 GateDecision 保持不可变，只重开 owner 和确定性后继。导演若要改变已批准脚本语义，必须回流编剧并重新形成 ScriptPackage，晋升为带 `parent_id` 的新 Script，同时使旧下游 package/manifest/plan 失效。
- Full Crew 后续制作必须复用既有画面生成、作品计划和作品级人工确认链路；操作者对 Prompt、主画面、模型、音色、声音模式、字幕、时间线或输出参数的修改必须作为 override diff 进入 WorkVersion/WorkPlan fingerprint，并重新规划确认，不得回写已批准 ProductionPackage。正式执行只展示并限制非金额资源用量，不得恢复金额估算。
- ProductionRun 必须真实传播 WorkGeneration 的成功、失败、人工处理、取消和结果不确定状态；取消或重试只能通过既有正式端口，不能直接改技术终态或重复提交 provider。Editor/QC 必须读取当前 WorkVersion 的 required take inventory、真实成片和不可变媒体证据；每个 take 按实际 segment 关联有序 Scene 集合及各 Scene 的适用 ShotContract 集合，不虚构 take/Shot 一对一关系，质量产物按 Run/WorkVersion 追加版本化。缺少确定性映射或适用视觉/音频能力时明确阻断，不得用文本评审、空结果或跨版本记录冒充真实质量检查。
- 当前范围不包含抖音、小红书等平台账号凭据、发布账号管理或 `accounts` 表改造；删除、归档、权限和多成员管理需要独立 OpenSpec change。

## 底层平台边界

以下能力是视频工作台依赖，但不应全部变成视频工作台前端菜单：

- `API Gateway / Backend`：统一 API、鉴权、业务编排入口。
- `AI Agent Orchestrator`：Agent 调度中枢。
- `Workflow Engine / DAG调度器`：任务拆解、并行执行、失败重试、状态机管理。
- `LLM / Multimodal Model Layer`：大语言模型、Embedding、TTS、Prompt 优化、第三方视频生成模型。
- `第三方AI模型生成平台`：Runway、Pika、可灵、HeyGen / Avatar。

平台配置、模型供应商、模型路由、API Key、MCP、Worker、队列、系统日志、权限、审计、成本和限额仍归 `admin/` 或后端控制面；`apps/video-agent/` 只展示与视频生产任务直接相关的状态、结果和操作。

## 开发阶段规划

### Phase 1：脚本创作闭环固化

- 保持当前 `脚本创作` 菜单为默认可用模块。
- 完成项目选择、脚本生成、脚本列表、时间轴对照详情、状态更新。
- 基于 `docs/prototypes/video-agent/video-agent.pen` 更新视频工作台原型。
- 验收：桌面端 E2E 覆盖品牌、菜单、3-12 分镜、无项目管理入口、时间轴对照视图。

### Phase 2：内容策略与选题池

- 新增 `内容策略` 菜单。
- 实现账号定位、用户画像摘要、选题池、热点/趋势占位、选题评分和选题确认。
- 接入或预留 `选题生成 Agent`。
- 验收：选题可进入脚本创作，脚本生成能引用已确认选题。
- 已确认第一版采用“选题池优先”：内容策略页展示项目策略摘要和选题池闭环，支持人工创建选题和选题 Agent 批量生成候选。选题状态为 `idea -> approved -> scripted -> archived`；Agent 生成结果自动入库为 `idea`，并记录 `generation_batch_id`。
- 2026-07-07 用户确认：内容策略的历史生成需要升级为独立列表页或独立二级视图；“历史生成”和“当前选题池”必须作为左侧业务菜单中“内容策略”下的二级菜单展示，且“历史生成”排在“当前选题池”上方，不放在主内容区形成独立菜单行。未生成脚本的选题可以从管理视图软删除，已生成脚本的选题不可删除。
- 2026-07-07 用户确认：历史生成列表页与当前选题池必须联动；在历史生成页选择某个生成批次后，返回或切换到当前选题池时应展示同一批次的选题内容，用历史页承担选题池批次切换入口。
- 2026-07-07 用户确认：历史生成页正式实现应采用三列结构，左列为历史生成批次，中列为当前主题选题，右列为补充操作；不得回退为批次详情和补充表单混在同一详情列的两列结构。
- 2026-07-07 用户确认：补充选题的产品口径是“同一个主题上下文，多次生成批次”。批次用于记录生成来源和审计，不是用户查看选题时的主分组；历史生成页和从历史页联动到当前选题池时，应按主题组聚合展示原始批次和补充批次的选题，并通过来源标签区分“原始生成/补充生成”。
- 选题 Agent 第一版接入通用 Agent Runtime 的 `topic` adapter，输入只依赖项目定位和用户补充要求，暂不依赖 `content_strategies` 或 `viral_videos`。
- 选题进入脚本创作前必须弹出生成参数确认面板，展示选题快照并确认 `style` 和 `scene_count`；脚本生成成功后写入 `scripts.topic_id` 和 `scripts.content.topic_snapshot`，并将选题状态更新为 `scripted`。
- 2026-07-07 用户确认：内容策略下一轮优化聚焦“选题太多不好筛”，正式设计方向为“主题组评审快照 + 双页面同步分层展示 + 第一版手动触发、自动预留”。评审对象是原始批次主题组，包含原始批次和补充批次的未软删除选题；评审输出优先推荐、可备选、建议淘汰、疑似重复、风险点和推荐/淘汰理由。评审结果必须在“历史生成”和“当前选题池”的同一主题组上下文同步展示；当当前选题池处于“查看全部选题”时不展示主题组评审分层。AI 评审只作为决策辅助，不得自动确认、归档、删除选题或改变 `ContentTopic.status`。
- 2026-07-08 用户确认：主题组质量排名第一版应服务“选出最值得立刻生成脚本的主题组”，正式口径为“脚本产出优先级排名”。历史生成页默认按脚本优先级展示主题组，并保留按时间排序；排名基于已有选题、补充批次归组和最新成功主题组评审快照做确定性计算，不在列表加载时额外调用 AI。未评审或评审过期的主题组只能提示待评审/需重新评审，不得排入“建议立刻出脚本”；排名不自动确认、归档、删除选题或改变 `ContentTopic.status`。
- 2026-07-08 用户确认：内容策略下一轮优化聚焦“Agent 生成选题质量不稳定”，采用“生成前策略约束 + 生成后质量闸门”的方向推进。第一版在 `topic` Agent 生成候选后、写入 `content_topics` 前执行质量闸门，覆盖账号匹配度、具体度、差异化、脚本化可行性、风险与评分可信度；首轮低质比例过高时最多自动重写一次，只把通过项写入选题池，淘汰候选只保留在质量报告中。该能力不得新增 `quality_rejected` 选题状态，不得改变 `idea -> approved -> scripted -> archived` 生命周期，也不得自动确认、归档、删除选题或生成脚本。
- 2026-07-08 用户确认：内容策略当前选题池在超宽桌面下不得让中间选题池无限拉伸；当前实现口径为内容策略工作区左对齐并封顶 `1800px`，三栏保持选题 Agent `360px`、选题池弹性但不超过约 `1040px`、详情栏在大屏放宽到 `420px`。`1440px` 桌面基准仍保持 `360/384/360` 三栏，不新增移动端适配。
- 2026-07-08 用户确认：内容策略下一轮进入“账号/策略资料沉淀”。第一版采用方案 A：继续使用 `projects` 作为后端内容账号边界，新增结构化 `strategy_profile`，字段覆盖目标受众、内容支柱、风格语气、禁区、参考账号和选题偏好；`projects.positioning` 仍作为账号定位摘要，`projects.description` 作为补充说明。选题生成、质量闸门和主题组评审必须读取同一份账号策略上下文。本轮不做平台发布账号凭据、不改造 `accounts` 表、不迁移既有 `project_id` 外键。用户进一步确认本版加入“AI 生成策略草稿，人工确认后保存”：AI 草稿只预填编辑表单并展示草稿摘要，保存前不得修改正式 `strategy_profile`；草稿生成只能手动触发，必须限制输出 token、最多一次临时错误重试，失败时不污染账号资料。用户最新纠正：账号策略资料只在内容策略下独立二级页面“账号策略”维护，当前选题池不得展示账号策略区块、策略资料状态/摘要或编辑入口；后续完整账号管理再单独拆出。

### Phase 3：素材管理与素材检索

- 新增 `素材管理` 菜单。
- 实现素材库列表、标签、素材候选、语义检索、素材替换和素材清单确认。
- 接入或预留 `素材检索 Agent`、Embedding 检索服务。
- 验收：脚本分镜可关联素材候选，素材清单可被作品生产读取。
- 素材库采用 `Konva.js + react-konva` 的画布工作台；`materials` 是归属 `projects.id` 的聚合根，画布节点由素材列表派生，不持久化节点位置或连线，也不表达 DAG 语义。
- 素材生命周期为 `active/archived`。进入素材库时不自动选中首条素材；详情抽屉按需打开，只编辑名称和标签，技术字段由系统维护。图片详情支持 50%-200% 大图预览。
- 素材正式入口使用文件上传：系统负责自管存储、稳定地址、类型识别和 metadata 提取，不再由操作者登记素材 URL 或编辑技术字段。
- 画面生成遵循“旧素材复用优先”：可用人物/IP 素材可作为参考图；AI 图片默认每分镜 3 张，可调整为 1-4 张，单次最多 `12 × 4 = 48` 张。未选候选也进入素材库并记录来源，所有生成结果必须先落入自管存储。
- 图片调用由 `services/video-worker` 异步执行；`backend` 负责校验、创建任务、记录状态和入库。视频工作台只选择 Admin 中启用的图片 `model_id`，PostgreSQL `ai_models` 是运行时唯一配置来源。
- 图片协议最终只允许 `openai_images | volcengine_ark_images`；Ark 使用 Bearer API Key。每个候选独立调用，单候选临时错误最多同模型重试一次，永久错误停止剩余调用，禁止自动跨模型切换。

- 2026-07-16 用户纠正并确认已有/上传音频调用 `volc.seedasr.auc` 时采用系统公用的私有 TOS 临时中转：TOS 归属 Admin“工具与 MCP”控制面，独立于全部 ASR 模型，系统维护一个启用的版本化配置供所有 ASR 模型共用；ASR 模型新增、编辑、停用和删除不得携带或受 TOS 配置约束。任务幂等上传并只提交短期签名 GET URL，任务终态后删除临时对象，清理失败保留审计并可重试；存在待清理对象时只阻止 TOS 配置变更或停用，不阻止模型 CRUD。TOS 只承担外部处理暂存，不替代素材库自管存储；凭据、签名 URL 和查询参数禁止进入快照、metadata、Agent 消息或日志。真实 Bucket 连接检查使用独立且默认关闭的 `TOS_TOOL_WORKER_ENABLED`，不得联动开启 TTS/ASR 任务消费。
- 2026-07-15 用户确认素材管理和作品生产的 6 个二级模块必须拆成 6 个独立 OpenSpec change，不得再合并为单一聚合 change：`extend-material-library-for-work-production`、`redefine-scene-visual-generation`、`add-sound-subtitle-generation`、`add-work-generation`、`add-work-generation-task-management`、`add-work-library-management`。每个 change 独立维护详细设计、规格、验收边界和未来任务。
- `add-sound-subtitle-generation` 已于 2026-07-17 经用户明确确认以 `45/47` 强制归档。声音/字幕主流程、系统 TOS 工具解耦、数据库 `route_path` 路由持久化和独立音色目录 Worker 已实现；真实 `ListSpeakers` 同步曾成功获取 14 页、415 个音色。
- 归档不代表真实供应商链路验收成功：用户明确放弃最小受控真实 TTS/ASR 验证和最终全量验收。归档前 TTS 尝试分别出现中转 HTTP 403 与另一中转域名 TLS `unexpected eof while reading`，ASR 未完成真实验证；恢复真实验收必须新建独立 OpenSpec change 并重新取得成本许可。

### Phase 5：发布运营与多平台分发

- 新增 `发布运营` 菜单。
- 各平台必须按实际获批的官方能力设计发布链路，不得把人工交接伪装成自动发布，也不得通过 Cookie、浏览器自动化或未公开接口绕过平台权限。
- 分发平台包括抖音 / TikTok、YouTube Shorts、B站、小红书。
- 验收：作品可按平台能力完成发布交接或官方 API 发布，并保存真实、可审计的发布结果；不同平台的自动化程度不得虚假统一。
- 2026-07-23 用户确认抖音个人开发者注册已通过，但个人开发者不能注册网站应用，因此当前不具备网站应用、H5 投稿或账号 OAuth 链路。用户进一步确认抖音个人账号采用官方创作者网页人工发布交接：系统负责校验并生成发布包、复制文案、打开抖音创作者中心，用户手工选择文件并确认发布，返回工作台后登记作品链接和发布结果。
- 当前抖音个人账号范围不建设抖音账号管理、多账号选择、自动排程、自动发布或发布结果同步，不建立无法通过官方接口验证的 `DouyinAccount` 聚合；只记录平台、作品版本、交接时间、最终作品链接和人工确认结果。后续若取得企业主体开放能力或接入具备官方资质的服务商，必须另行提出 OpenSpec change 扩展账号授权和自动发布。
- 2026-07-23 用户确认小红书采用与抖音相同的官方网页人工发布交接边界：系统生成发布包和文案并打开小红书官方创作者入口，用户手工选择文件并确认发布，返回工作台后登记作品链接和发布结果。当前不建设小红书账号管理、多账号选择、自动排程、自动发布或发布结果同步，也不建立无法通过官方接口验证的 `XiaohongshuAccount` 聚合；后续取得官方开放能力或具备资质的服务商接入时，必须另行提出 OpenSpec change。
- 不得记录或要求用户提供抖音或小红书的 Cookie、Token、密钥等敏感凭据。
- 2026-07-23 用户确认人工发布首期不校验抖音、小红书的平台文件大小、时长、封面尺寸和文案字数限额；公开页面未提供可稳定引用的限额契约，禁止猜测或硬编码。系统仍须校验本地 artifact 完整性、平台所需文件、官方入口、HTTPS 官方作品链接和人工确认结果；平台限额核验须在获得可核验官方规则后另行变更 profile 版本。

## 前端实现原则

- 一级菜单以业务流程为主：内容策略、脚本创作、素材管理、作品生产、发布运营、数据分析、工作流任务。
- 当前六类 Agent 能力可以作为二级菜单、菜单分组或模块状态继续保留，但页面一级导航必须反映视频生产业务流，并由数据库菜单配置驱动。
- 每个菜单必须有明确的空状态、加载状态、错误状态和任务状态。
- 不在 `apps/video-agent/` 中加入模型 Key、模型路由、MCP 管理、Worker 队列、系统日志、权限审计等平台控制面配置。

**How to apply:** 后续新增视频工作台功能时，先判断属于上述哪个一级菜单和开发阶段；如需要跨阶段推进，必须先提出 OpenSpec change，更新 `docs/prototypes/video-agent/video-agent.pen` 后再实现。
