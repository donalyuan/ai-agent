## Context

现有 `topic_generation_batches` 表达一次选题 Agent 批量生成记录。当前选题 Agent 每次生成都会创建新批次，并将生成出的 `content_topics.batch_id` 指向该批次。历史生成页已经能按批次查看选题、移除未成稿选题，并且批次计数只统计未软删除选题。

新需求要求已经生成过选题的历史批次可以再次补充选题。用户已确认采用“原批次的补充批次”语义：补充生成是新的批次，但和原批次有关联。

## Goals / Non-Goals

**Goals:**

- 支持从历史生成批次发起补充选题。
- 保持原始批次不可变，不把新选题直接写回原始批次。
- 将补充结果记录为新的 `topic_generation_batches`，并关联原始批次。
- 补充生成调用 LLM 时必须带入原始生成要求和同主题组已有选题，确保新候选是在同一主题下扩展。
- 历史生成页能展示和切换原始批次、补充批次。
- 保持现有软删除、状态筛选、评分排序和项目隔离规则。

**Non-Goals:**

- 不展示失败批次或空批次作为可补充目标。
- 不提供跨项目补充。
- 不改写已应用 migration。
- 不改变脚本生成和选题 `scripted` 状态流转。
- 不实现移动端适配。

## Decisions

### 1. 使用新批次承载补充生成

补充生成 SHALL 创建新的 `topic_generation_batches`。新批次的 `supplement_of_batch_id` 指向原始批次，新选题的 `content_topics.batch_id` 指向补充批次本身。

原因：`topic_generation_batches` 是一次生成事件。把补充选题直接挂回原批次会让原批次的 `prompt`、`requested_count`、`source_run_id` 与实际选题集合不一致，破坏审计语义。

备选方案：把新选题直接追加到原批次。实现简单，但无法区分原始生成和补充生成，不利于追溯。

### 2. 字段命名采用 `supplement_of_batch_id`

新增字段：

```sql
ALTER TABLE topic_generation_batches
    ADD COLUMN supplement_of_batch_id UUID REFERENCES topic_generation_batches(id) ON DELETE SET NULL;
```

该字段为空表示普通原始批次；非空表示补充批次。字段必须通过新 migration 添加，不能修改已应用 migration。

### 3. 补充目标必须可管理

后端发起补充前必须校验目标批次：

- 目标批次存在。
- 目标批次属于当前项目。
- 目标批次状态为 `succeeded`。
- 目标批次当前仍有未软删除选题。

原因：失败批次、空批次和跨项目批次不应作为历史生成管理入口，也不应作为补充目标。

### 4. 补充批次归入同一个原始上下文

如果补充批次再次被补充，展示层应归入同一个原始批次上下文。后端可接受补充批次作为目标，但创建新批次时应把 `supplement_of_batch_id` 归一到最初的原始批次。

原因：避免形成深层链式 UI，历史页只需要“原始批次 + 补充批次列表”的稳定结构。

### 5. 前端在历史详情发起补充

历史生成详情页增加“补充选题”入口。提交成功后刷新批次列表、当前主题组选题和统计，并选中新创建的补充批次；选题展示按原始批次 + 关联补充批次聚合，批次只作为生成来源和审计记录。

原因：补充动作依赖历史批次上下文，放在历史详情页比放在全局选题 Agent 面板更明确。

### 6. 补充生成必须注入主题上下文

补充生成 SHALL 在调用 LLM 前读取原始批次 prompt、同主题组下已有未软删除选题，以及当前会话中本轮之前的历史消息摘要。Prompt 必须明确要求基于同一主题继续扩展，并避免重复已有选题。

原因：`supplement_of_batch_id` 只解决数据归属和审计关系；如果不把原始主题上下文传给 LLM，补充生成只能依赖当前补充要求和项目定位，无法稳定保证新选题与原始主题相关。

## Risks / Trade-offs

- [Risk] 批次列表层级变复杂。解决：前端只展示一层“原始批次 + 补充批次”，后端归一补充根批次。
- [Risk] 补充生成失败后历史页状态不一致。解决：失败批次仍不作为历史入口展示，前端展示错误并保留当前批次。
- [Risk] 已有批次统计被补充批次混淆。解决：原始批次 `topic_count` 只统计自身选题，补充批次单独统计。
- [Risk] 并发补充同一批次。解决：每次补充都是独立批次，不需要覆盖原批次。

## Migration Plan

1. 新增 migration，为 `topic_generation_batches` 添加 `supplement_of_batch_id`、注释和索引。
2. 扩展批次模型、repository 查询和响应 DTO。
3. 扩展 topic Agent runtime，支持补充生成输入、目标校验和 metadata 输出。
4. 更新历史生成页原型并获得明确开发确认。
5. 实现历史页补充入口、补充表单、补充批次展示和刷新逻辑。
6. 运行后端、前端和 OpenSpec 验证。
