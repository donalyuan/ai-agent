## Context

`work_generation_repository::save_plan` 当前在每次保存计划时执行 `MAX(version_no) + 1` 并插入 `work_versions`，随后只失效旧计划，未复用旧计划关联的未运行草稿。作品库的“继续修改”已经能复用同一来源的编辑草稿，但整体重生成仍可能重复派生。详情页面则递归展开全部 snapshot，并让主区与版本栏分别滚动。

作品版本必须同时满足两个目标：已确认/已运行事实不可变，未确认规划可以持续修订。版本号应表达新的生产意图，而不是内部计划保存次数。

## Goals / Non-Goals

**Goals:**

- 同一生产意图只保留一个可变草稿，计划重算只递增 `work_plans.plan_version`。
- 新生产意图仍创建新版本，并保留来源、派生类型和不可变运行事实。
- 安全清理历史冗余草稿，不删除任何运行、调用、产物、差异或发布审计。
- 详情首屏只呈现业务决策、当前产物和可操作版本；技术字段渐进披露。
- 页面主体和版本栏保持固定高度，版本历史可分组折叠；历史展开内容使用限定区域局部滚动，不带动整个详情卡片增长。
- 当前草稿通过作品 Agent 自然语言对话持续修改，并在同一草稿上生成可确认的结构化差异。
- 详情业务工作区严格映射已确认的 v3 Pencil 原型。

**Non-Goals:**

- 不删除或合并已确认、运行中、完成、失败版本。
- 不改变 generation DAG、provider 重试和发布运营状态机。
- 不新增金额、价格、币种或费用字段。
- 不覆盖移动端适配。
- 不修改全局顶栏、品牌区、左侧菜单宽度和内容起点。
- 不在作品详情暴露 `prompt_snapshot` 原始表单、手工“保存草稿修改”或手工“分析版本差异”入口。
- 不由作品 Agent 自动触发视频、TTS、ASR、发布或其他可能产生外部资源消耗的下游能力。

## DDD

`Work` 仍是聚合根。`WorkVersion` 的 `draft` 表示一个尚未锁定的生产意图；`work_plans` 表示该意图内多次计算得到的计划修订。版本派生键为：

- 初始规划：`work_id + initial`。
- 继续修改：`work_id + source_version_id + edit`。
- 整体重生成：`work_id + source_version_id + full_regeneration`。

同一派生键已有可编辑草稿时复用该草稿。确认运行把草稿锁定为运行事实，之后同一作品的新规划必须建立新的派生草稿。失败版本属于真实运行事实，不能退回草稿或清理。

`WorkAgentConversation` 是绑定 `project_id + subject_type=work + subject_id=work_id` 的连续修改会话。它读取当前所选来源版本与当前编辑草稿，把自然语言意图转换为 `WorkVersion` 快照白名单补丁，但版本复用、差异分析和确认规则仍归作品领域服务。

## BDD

操作者反复要求 Agent 调整同一规划时，版本号保持不变，只看到计划内容和更新时间变化。从完成或失败版本发起新的整体重生成时创建一个草稿；同一来源重复进入该重生成意图时返回已有草稿。从完成版本继续修改时遵循同样规则。

作品详情默认显示当前草稿和可用成片；失败版本与早期草稿归入折叠历史。当前草稿没有运行产物时只显示紧凑空状态，不渲染空轨道。模型 ID、trace 和原始参数位于可展开技术快照内。

当 V11 是来源于 V5 的当前 `edit` 草稿时，操作者输入“保留配音，让画面节奏更紧凑”，系统更新 V11 而不创建 V12，返回 Agent 回复和等待确认的差异。模型输出非法、包含未知字段或补丁为空时，页面显示失败并保留用户消息，作品草稿不得发生变化。

## SDD

### 保存计划事务

`save_plan` 先以 `FOR UPDATE` 锁定 `works`。若当前版本为 `draft` 且没有 generation run，则更新同一版本的 input/model/parameter/timeline/prompt snapshot；否则按当前不可变版本派生 `full_regeneration` 草稿，没有历史版本时创建 `initial` 草稿。事务继续插入新的 `work_plans` 修订、失效旧的 `draft/ready` 计划，并把 `works.current_version_id` 指向草稿。

作品库派生版本按 `work_id + source_version_id + derivation_kind + status=draft` 查找并锁定；`edit` 与 `full_regeneration` 都复用相同派生键的草稿。作品行锁负责串行化并发创建，数据库测试验证同一意图不会产生两个版本。

### 历史清理

一次性 migration 先为每个尚无当前草稿的未运行作品选择最新 `ready/draft` 计划对应版本作为保留草稿并更新 `current_version_id`。其余候选只有同时满足以下条件才可删除：

- 版本状态为 `draft`，不是 `works.current_version_id`。
- 关联计划全部为 `invalidated`，且没有 generation run、step 或 provider attempt。
- 没有 artifact、timeline、diff plan、diff confirmation 或 publication handoff。
- 没有其他版本通过 `source_version_id` 引用。

migration 先删除候选关联的 invalidated plan，再删除版本。任何不满足谓词的草稿原样保留并归入前端历史，不采用级联删除或忽略约束。

### 详情呈现

前端从现有 `current_version_id`、版本状态、派生类型、run 和 artifact 数据确定三组：当前草稿、可用成片、失败与早期记录。业务摘要使用显式字段映射，不再递归渲染 snapshot。技术快照保留完整数据，但默认折叠并按需展开。

详情工作区由主业务区和固定宽度、固定高度的版本侧栏组成。主业务区不设置独立纵向滚动；版本侧栏只允许“失败与早期记录”的展开内容在剩余空间内滚动，当前草稿、可用成片、分组标题、操作区和 Agent 区保持固定。空时间轴只渲染标题、状态和来源版本入口。

原型基准为 `docs/prototypes/video-agent/video-agent.pen` 中“桌面宽屏 - 作品详情 Agent 对话 v3 半版待确认”。正式实现保留全站统一骨架，在内容区内映射页面说明区、52px 主操作栏、主业务区、400px 版本栏、版本卡片和 Agent 会话区。详情卡片不因历史版本数量增长；历史展开内容使用版本栏内唯一的限定滚动区。

### 作品 Agent Runtime

会话创建和发送消息都校验作品属于会话绑定项目。每轮只允许一次文本模型调用且不自动重试；Prompt 要求输出包含 `assistant_message` 和五类可选 snapshot patch 的 JSON。Runtime 对字段白名单、类型和非空补丁做严格校验，通过后调用 `derive_version(..., "edit", patches)` 复用当前编辑草稿，再调用 `analyze_diff`。

Assistant 消息 metadata 保存 `draft_version_id`、`version_no`、完整 diff 和 `requires_confirmation=true`。前端据此刷新详情并提供“查看影响并确认”入口；确认仍复用现有 diff 确认接口。任何解析、归属校验或持久化失败都不自动调用下游生成能力。

## TDD

- Repository：首次规划、重复规划、运行后再规划、同来源编辑/整体重生成复用和并发保存。
- Migration：安全候选被清理；存在 run、attempt、artifact、timeline、diff、发布或来源引用时保留；失败版本始终保留。
- API：详情继续返回明确当前版本和完整历史，清理后引用完整。
- Frontend：业务摘要字段映射、技术快照折叠、空/非空时间轴、三组版本及正确数量。
- E2E：连续重新规划版本号不增长；选择当前草稿/完成版本；展开失败历史；详情 Surface 高度保持不变，历史列表内部可滚动且不覆盖固定操作区，原始 UUID 不在首屏铺陈。
- Work Agent：作品归属校验、结构化输出白名单、非法/空补丁不落库、复用当前编辑草稿、生成 diff metadata、单轮单次文本调用且不触发下游生成。
- Frontend v3：自然语言消息发送与失败保留、成功后刷新草稿、diff 确认入口、旧手工表单和按钮消失；在 `1920x980` 对照原型验证 52px 操作栏、400px 固定版本栏、历史限定滚动区和无重叠。

## Decisions

### 版本与计划修订分离

选择复用 `draft WorkVersion`、新增 `WorkPlan` 修订。备选方案是每次规划继续创建版本并只在 UI 隐藏，但该方案不能阻止数据库膨胀，也会污染版本语义。

### 使用作品行锁串行化

所有创建或复用判断在锁定 `works` 后执行。相比仅在应用层先查后写，该方案可以消除并发竞态；相比新增复杂 intent session 表，现有来源与派生类型已足以表达当前边界。

### 清理采用完整否定谓词

只清理从未形成外部或下游事实的失效草稿。相比按状态或时间直接删除，完整引用检查能保留所有可能参与审计的版本。

### 技术数据渐进披露

技术 snapshot 继续可访问但不占据首屏。相比删除技术信息，该方案兼顾运营扫描和故障审计。

### 使用完整作品 Agent 流程而非聊天皮肤

拒绝只把原提示词表单换成聊天样式的方案。Agent 必须完成受约束 patch、草稿复用、差异分析和确认入口，确保对话是作品修改的真实业务入口，而不是与手工流程并存的装饰界面。

## Risks / Trade-offs

- [历史数据存在未识别引用] -> migration 使用显式 `NOT EXISTS` 和外键约束，无法证明安全的记录不删除。
- [并发规划创建重复草稿] -> 事务首先锁定作品行，并增加并发数据库测试。
- [折叠历史导致失败不易察觉] -> 分组标题显示失败数量，当前选中失败版本仍在主区展示失败摘要和任务入口。
- [单滚动后侧栏内容较长] -> 历史默认折叠，操作随所选版本显示，避免侧栏无限增长。
- [LLM 返回非法或越权字段] -> 使用 JSON 契约、字段白名单和服务端严格校验，失败不落库并保留用户输入供人工重试。
- [外部调用造成非预期资源消耗] -> 每轮最多一次文本模型调用、不自动重试、不自动调用视频/TTS/ASR/发布。

## Migration Plan

1. 增加 migration，规范 `current_version_id` 并按安全谓词清理失效草稿。
2. 修改计划保存与版本派生事务，先完成数据库测试再切换业务入口。
3. 接入作品 Agent Runtime，并按确认后的 v3 原型修改详情页面和测试。
4. 运行 Rust workspace、前端单测和作品库 E2E。
5. 回滚代码时保留已复用的草稿与不可变版本；已安全删除的冗余草稿不作为业务事实恢复。
